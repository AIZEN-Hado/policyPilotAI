# Production readiness plan

Reviewed: 2026-11-07. Scope: static repository inspection; no application changes, dependency installation, tests, inference, or deployment performed. Two shared reference files named by the analysis skill were unavailable.

## Assessment and assumptions

The repository is a local prototype, not ready for real claim processing. Plan the first release as an internal, single-organization assistant with human approval of coverage recommendations. Hosting, concurrency, jurisdiction, retention, and recovery objectives remain to be defined. This assessment does not establish legal compliance or model accuracy.

Current flow: Streamlit -> FastAPI -> synchronous FAISS retrieval and Ollama inference -> SQLite claim/decision/audit persistence. PDF ingestion rebuilds a local FAISS index. There are no training entrypoints; inference is in app/decision_engine.py, ingestion in app/rag/ingest.py, configuration in app/config.py, and mocked checks in tests/.

## Ordered implementation plan

1. Establish a reproducible baseline. Select the supported Python runtime, resolve and lock the complete dependency graph, and run clean-install checks. Fix the FAISS test patch target and isolate API tests with a temporary database and explicit lifespan setup. Add CI for tests, linting, dependency and secret scanning. Gate: a clean checkout installs and passes checks without production data or model downloads in unit tests.
2. Secure access and data. Integrate authenticated identities; enforce claim ownership/organization scope and reviewer/admin roles at every API route. Restrict ingestion to admins. Add TLS at the ingress, explicit CORS origins, bounded inputs/pagination, rate limits, safe errors, and production configuration validation. Define retention, deletion, access audit, encrypted storage/backups, and redacted logs. Gate: unauthenticated and unauthorized access, including direct claim IDs, is denied in integration tests.
3. Make recommendations evidence-bound. Introduce authoritative policy IDs, versions, effective dates, and claim-to-policy assignment. Scope retrieval before ranking. Preserve document hashes, pages, chunk IDs, and real retrieval scores. Validate citations against retrieved evidence; use typed structured output and deterministic abstention for missing, conflicting, irrelevant, or invalid evidence. Record model digest, prompt version, index version, and review actions. Remove the implication that self-reported model confidence is measured accuracy. Gate: wrong-policy retrieval is rejected, unsupported citations fail validation, and missing evidence cannot produce a final coverage outcome.
4. Make processing reliable. Move long-running inference and ingestion into bounded workers with persistent job states, timeouts, idempotency, retry rules, and failure reporting. Avoid blocking the API event loop. Build immutable index versions, validate before atomic publication, and refresh reader caches safely. Protect index artifacts from untrusted writes. Handle empty/scanned/corrupt PDFs and extraction limits explicitly. Gate: worker restart, duplicate submission, concurrent ingestion, missing index, and Ollama outage tests preserve consistent state and recover predictably.
5. Package and operate the service. Add reproducible container builds, private networking for Ollama/data services, persistent volumes, migrations, separate liveness/readiness checks, structured redacted logs, request/job IDs, metrics, alerts, and backup/restore procedures. Configure UI endpoints through environment settings and bundle external UI assets for offline operation. SQLite/FAISS can remain for a bounded single-host pilot after concurrency and restore validation; choose a shared transactional database before multi-instance operation. Gate: staging install, migration, restart, restore, and rollback rehearsals succeed.
6. Validate and release gradually. Build a domain-reviewed evaluation set covering exclusions, dates, endorsements, conflicting clauses, missing evidence, and prompt injection in claims/documents. Measure retrieval recall, citation correctness, false coverage/denial recommendations, abstention, and human overrides by scenario. Benchmark real target hardware for latency, throughput, memory, and queue depth. Agree numerical quality and capacity thresholds before release. Start with shadow mode, then a restricted pilot with mandatory human review. Gate: agreed thresholds pass and an accountable owner signs off on operations and evaluation results.

## Scope decisions

Keep FastAPI, Ollama, and the existing UI for the first pilot. A UI rewrite, new model, or vector database migration should follow measured need. Public access, multiple organizations, autonomous adjudication, or high availability substantially expand the work.

Indicative planning estimate: 4–6 engineering weeks for a restricted internal pilot, assuming one experienced engineer, available infrastructure/identity integration, and timely domain review. This is not a delivery commitment; model evaluation and unresolved deployment requirements may extend it.
